## When to use

A capability needs its first specification, a change needs a delta spec describing the future
state, or an existing spec is under review before G2-SPEC.

## Rules

1. Write the delta spec at `delivery/changes/<name>/specs/<capability>/spec.md`. It states the
   **future** state of the capability, not the diff. `archive` folds it into
   `delivery/specs/<capability>/spec.md`, which is current truth.
2. Never edit `delivery/specs/` directly during a change. Current truth changes only at
   archive; a hand-edit there makes the spec describe something that was never gated.
3. Put every `REQ-###` on a Markdown heading line. The validator recognises a requirement only
   when the id appears on a line starting with `#`.
4. Number requirements `REQ-###` with at least three digits, sequential within the capability,
   never reused after deletion.
5. Give every requirement a MoSCoW priority on its own line: `**Priority:** Must | Should |
   Could | Won't`. A requirement with no priority is not prioritised, it is just first.
6. Cap `Must` at the set the change genuinely cannot ship without. When everything is `Must`,
   nothing is.
7. Record each `Won't` explicitly with the reason. A `Won't` is the durable form of a
   non-goal and is what stops the same scope returning next quarter.
8. State every requirement as observable behaviour of the system, in the present tense, from
   the outside. Never as an implementation, a task, or a team activity.
9. Write one requirement per behaviour. A requirement containing "and" between two outcomes is
   two requirements.
10. Include all five non-functional sections in every spec, each either populated or carrying
    an explicit `Not applicable — <reason>`: performance, security and privacy, reliability,
    observability, accessibility and compatibility. A blank section is a gap, not a nil.
11. Record every unresolved point as `Q-###` under `## Open questions`, with the decision it
    blocks and who can answer it. Never resolve a question by assumption inside a requirement.
12. Define every domain term the first time it appears, under `## Glossary`. Two words for one
    thing is the commonest source of a wrong build.
13. Write acceptance criteria under each requirement's heading per
    `navi-skill-acceptance-criteria`. A requirement with no criterion cannot pass G2.

## Decision table

| Observed in the draft | Required action |
|---|---|
| A requirement naming a table, class, queue or library | Rewrite as external behaviour; the mechanism belongs in `design.md` |
| A requirement phrased as an activity ("migrate the users table") | Rewrite as the behaviour the migration produces, or move it to `tasks.md` |
| "and" joining two outcomes in one requirement | Split into two consecutively numbered requirements |
| A requirement with no `**Priority:**` line | Assign a MoSCoW priority |
| Every requirement marked `Must` | Re-prioritise; name what the change could ship without |
| A non-functional section left empty | Populate it, or write `Not applicable — <reason>` |
| An unstated performance expectation | Write the threshold, percentile, window and environment, or raise a `Q-###` |
| PII present and no privacy section | Blocking — classify the data and state its handling before G2 |
| An assumption embedded in a requirement | Move it to `Q-###`, or state it under `## Assumptions` |
| A domain term used two different ways | Pick one, define it in `## Glossary`, rewrite both uses |
| A requirement that no acceptance criterion can express | Not specified yet — raise it as a `Q-###` |
| `delivery/specs/` edited mid-change | Revert; put the change in the delta spec |

## Template

```markdown
# Capability — Theme preference

**Status:** delta for change `theme-persistence`
**Owner:** <named requirement owner>

## Context

Signed-in users choose a theme and lose it on the next page load, because the preference is
held only in memory. This capability makes the choice durable.

## Requirements

### REQ-001 — Theme preference persists across sessions
**Priority:** Must
**Source:** Elicited from ACTOR-001, 2026-09-18

A signed-in user's chosen theme is reapplied on every subsequent page load, on every device
where they are signed in.

#### AC-001
Given a signed-in user with a saved theme preference,
when they load any page,
then the saved theme is applied before first paint.
Implements: REQ-001

### REQ-002 — Absent preference falls back to the system scheme
**Priority:** Must
**Source:** Elicited from ACTOR-001, 2026-09-18

#### AC-002
Given a signed-in user with no saved preference,
when they load any page,
then the operating-system colour scheme is applied and no preference is written.
Implements: REQ-002

### REQ-003 — Preference survives a preference-store outage
**Priority:** Should
**Source:** Inferred — ASSUM-001

#### AC-003
Given the preference store is unreachable,
when a signed-in user loads any page,
then the light theme is applied and one warning is logged with the user id omitted.
Implements: REQ-003

### REQ-004 — Per-device theme override
**Priority:** Won't
**Source:** Elicited from ACTOR-002, 2026-09-19

Not in this change: a per-device override needs a device identity the product does not have.
Revisit when device registration ships.

## Non-functional requirements

### Performance
Preference read adds no more than 20ms at p95 to the page's time to first paint, measured in
the browser over a 24-hour window on the production traffic mix.

### Security and privacy
The theme preference is not personal data under the project's classification. It is stored
against the user id and is never written to logs. No new data category is introduced, so the
existing retention and deletion policy applies unchanged.

### Reliability
A preference-store outage degrades to the light theme, never to an error page. Availability
target is inherited from the settings service; no new objective is introduced.

### Observability
`SLI-001` measures the proportion of page loads where the saved theme is applied before first
paint. An alert fires when the 28-day objective is at risk.

### Accessibility and compatibility
The high-contrast theme is reachable by keyboard alone. Behaviour is identical on the two
most recent major versions of the supported browsers.

<!-- Every section above is populated, because on this change every one of them applies.
     A section that genuinely does not apply takes the other form — the single line and
     nothing else, like this:

         ### Security and privacy
         Not applicable — no data is read, written or transmitted by this change.

     Populated or the one N/A line. Never a substantive answer followed by an N/A line:
     a reader cannot tell which of the two the author meant. -->

## Assumptions

- Signed-in users are identified by the existing session user id. Confirmed with the identity
  owner on 2026-09-24.

## Open questions

- **Q-012** Is a 30-second stale window acceptable for the high-contrast theme?
  Blocks: the caching decision in ADR-004. Answered by: the accessibility owner.

## Glossary

- **Theme** — the named colour scheme a user selects, one of `light`, `dark`, `high-contrast`.
- **Preference** — the durable record of a user's theme choice. Distinct from the *applied*
  theme, which may differ during a store outage.

## Non-goals

- Themeing the transactional email templates.
- A theme editor. Only the three named themes exist.
```

## Checklist

- [ ] The spec is in the change's delta path, and `delivery/specs/` is untouched
- [ ] Every `REQ-###` is on a heading line, three digits, sequential, never reused
- [ ] Every requirement carries a MoSCoW priority
- [ ] `Must` is limited to what the change cannot ship without
- [ ] Every `Won't` carries its reason
- [ ] Every requirement is external, observable, present-tense behaviour
- [ ] No requirement joins two outcomes with "and"
- [ ] All five non-functional sections are populated or explicitly not applicable
- [ ] Every requirement has at least one acceptance criterion under its own heading
- [ ] Every unresolved point is a `Q-###` naming what it blocks and who answers it
- [ ] Every domain term used more than once is in the glossary
- [ ] `validate_traceability.py` reports no T2 findings

## Anti-patterns

**Spec as design.** `REQ-005 — Store the preference in a Redis hash keyed by user id.` That is
a mechanism, and it forecloses the design before G3. Write
`REQ-005 — The preference is readable within 20ms at p95` and let `design.md` choose Redis.

**Spec as task list.** `REQ-006 — Update the settings page component.` An activity, not a
behaviour. It belongs in `tasks.md` under a requirement that states what the user then
experiences.

**Everything is Must.** Fourteen requirements, fourteen `Must`. The priority column now carries
no information and the first thing cut under pressure will be cut arbitrarily. Decide what the
change could ship without.

**Empty NFR sections.** Five headings with nothing under them. A reader cannot distinguish
"considered and not applicable" from "never thought about". Write
`Not applicable — <reason>` where it truly does not apply.

**Assumption disguised as a requirement.** `REQ-008 — The system supports 500 concurrent
users.` If 500 is measured, it is a requirement with an instrument; if it is a guess, it is an
assumption or a `Q-###`. Say which.

**Delta written as a diff.** `REQ-002 — change the fallback from dark to light.` A delta spec
states the future state so that folding it into `delivery/specs/` produces a readable spec.
Write `REQ-002 — Absent preference falls back to the system scheme`.

**Direct edit to current truth.** Changing `delivery/specs/theme/spec.md` during the change
because it is faster. Current truth then describes behaviour no gate ever examined, and the
archive fold silently overwrites it. Put the change in the delta.

**Two words for one thing.** "Preference" and "setting" used interchangeably across the spec.
Two engineers build two models. Pick one, define it, rewrite the other uses.

## Validation

```bash
python3 scripts/validate_traceability.py delivery/        # T2 must be clean
navi-delivery validate                                     # runs all three validators
```

Confirm every requirement is on a heading line and carries a priority:

```bash
# Summed across every spec.md under the change, and compared rather than printed:
# `grep -rc` prints one count per file, so two bare listings cannot be compared by eye
# once a change has more than one capability.
CHANGE=<name>
count() { grep -rcE "$1" --include=spec.md delivery/changes/$CHANGE/specs \
            | awk -F: '{n += $NF} END {print n + 0}'; }
headings=$(count '^#+.*REQ-[0-9]{3,}')
priorities=$(count '^\*\*Priority:\*\*')
[ "$headings" -eq "$priorities" ] \
  || echo "$headings requirement heading(s) and $priorities '**Priority:**' line(s) — every requirement carries one"
```

The two counts must be equal. A requirement not on a heading is invisible to the validator; a
requirement with no priority is unprioritised.

Confirm every non-functional section exists:

```bash
for s in Performance "Security and privacy" Reliability Observability \
         "Accessibility and compatibility"; do
  grep -rq "### $s" --include=spec.md delivery/changes/<name>/specs || echo "missing NFR section: $s"
done
```
