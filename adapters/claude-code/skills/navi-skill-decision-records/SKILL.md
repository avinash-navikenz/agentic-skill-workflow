## When to use

A design choice is being made at Phase 3, a choice already recorded is being reversed, a
threat is being accepted rather than mitigated, or G3 is about to be recorded and each
consequential decision needs a file to point at.

## Rules

1. Write one decision per file at `delivery/decisions/ADR-###.md`, three digits minimum,
   allocated sequentially across the whole repository and never reused after a deletion. The
   directory is scaffolded by `navi-delivery init`; the number is the permanent handle that
   handoff envelopes, `design.md` and gate evidence refer to.
2. Write an ADR for every decision that is **consequential**, and for no decision that is not.
   A decision is consequential when reversing it after G5 would require any one of: changing
   code in more than one component, migrating stored data, or changing an interface a
   consumer outside this change already calls. A decision failing all three is implementation
   and belongs in the code.
3. Give every ADR all seven headings, in this order: `Status`, `Context`, `Decision`,
   `Alternatives rejected`, `Consequences`, `Binds`, `Review`. A missing heading is a missing
   section, not an implied empty one.
4. Set `Status` to exactly one of `Proposed`, `Accepted`, `Rejected`, or
   `Superseded by ADR-###`. There is no `In progress`, no `Draft`, and no `Accepted with
   caveats` — a caveat is either a consequence or a second ADR.
5. Name at least one rejected alternative, each with the reason it lost stated as a property
   of the alternative rather than a property of the decision taken. An ADR with no rejected
   alternative records a default, not a decision — delete it, or find the option that was
   passed over.
6. Write at least one consequence that is worse than the status quo. Every consequential
   decision costs something; an ADR whose consequences are all benefits has not been
   examined, and the cost will be discovered by whoever operates it.
7. Bind every ADR to what motivated it with a `Binds:` line naming the `REQ-###` ids, the
   change name, or both. An ADR that binds to nothing cannot be found by the person who later
   changes the requirement it served.
8. Never edit the `Decision` or `Alternatives rejected` of an ADR whose status is `Accepted`.
   Reversing an accepted decision means writing a new ADR and setting the old one's `Status`
   to `Superseded by ADR-###` — one line changes, nothing else.
9. Record every threat accepted at G3 as its own ADR carrying an `Accepted-risk:` line and an
   `Accepted-by:` line naming a person, not a role and not an agent. `references/gates.md`
   accepts the threat model plus these ADRs as G3 evidence; an accepted threat with no named
   acceptor fails that criterion.
10. Set `Review:` to a date or to a named trigger event — never to `periodically`. A decision
    taken under an assumption that may expire carries the date the assumption is re-tested.
11. Link every ADR the design depends on from `delivery/changes/<name>/design.md` by id. G3
    reads the design; an ADR nothing links to is invisible to the gate.
12. Write ADRs before recording G3, not after. An ADR written to satisfy a gate already
    recorded documents a decision that was never open.

## Decision table

| Observed condition | Required action |
|---|---|
| Reversal after G5 would touch two or more components | Write an ADR before building |
| Reversal would require a data migration | Write an ADR before building |
| Reversal would change an interface an outside consumer calls | Write an ADR before building |
| Reversal is a local edit inside one module | No ADR — record the reasoning in the code |
| The choice has no rival option | No ADR — record the constraint in `design.md` `## Approach` |
| A threat is being accepted rather than mitigated | ADR with `Accepted-risk:` and `Accepted-by: <person>` |
| An accepted ADR's decision is being reversed | New ADR; set the old to `Superseded by ADR-###` |
| The same ADR number already exists on disk | Allocate the next unused number; never reuse |
| `design.md` names `ADR-012` and no such file exists | Write the ADR or remove the reference before G3 |
| Consequences list contains only benefits | Name the cost, or the decision was not examined |
| Decision depends on an assumption that may expire | Set `Review:` to the date or the triggering event |
| G3 is recorded and a consequential decision has no ADR | Re-record G3 as `--fail`; write the ADR, then re-record |

## Template

Copy into `delivery/decisions/ADR-007.md` and replace the content, not the headings:

```markdown
# ADR-007 — Store theme preference server-side rather than in localStorage

## Status
Accepted

## Context
REQ-001 requires a signed-in user's theme to apply before first paint on any device. The
current client reads `localStorage`, which is per-device and unavailable before hydration.
Peak load is 500 rps (assumed, 2026-Q2 capacity note); the preference is read on every page
load.

## Decision
Persist the preference on the user record and serve it in the session payload that renders
the shell, so the theme is known before first paint and travels with the account.

## Alternatives rejected
- **Keep `localStorage`.** Per-device by construction, so it cannot satisfy REQ-001 on a
  second device, and it is unreadable before hydration.
- **A dedicated preferences service.** Adds a network hop on the critical render path and a
  new failure mode on a payload of one boolean.
- **Cookie written by the client.** Satisfies first paint but is unauthenticated, so a
  hostile cookie changes what the server renders.

## Consequences
- The preference now lives in the user record, so exporting or deleting a user account has
  one more field to cover, and the user schema gains a column this change did not budget for.
- Every session-payload read now depends on the user store: when it is unreachable, AC-003's
  light-theme fallback is the behaviour, and that path is now on the critical render path.
- Changing the preference requires a round trip, so the toggle needs an optimistic update
  that AC-002 does not specify.

## Binds
REQ-001, REQ-004; change `theme-persistence`

## Review
2027-03-31, or earlier if session payload p95 exceeds the 120ms budget in QAS-002.
```

An ADR recording an accepted threat:

```markdown
# ADR-009 — Accept unauthenticated read of the public status endpoint

## Status
Accepted

## Context
THREAT-004 in `delivery/changes/theme-persistence/threat-model.md`: an anonymous caller can
enumerate deployment ids through `/status`. Mitigating it means authenticating a route four
external monitors already poll.

## Decision
Accept the exposure for this change. Deployment ids are already visible in the release notes
feed, so the threat reveals nothing the same caller cannot read elsewhere.

## Alternatives rejected
- **Authenticate `/status`.** Breaks four external monitors whose owners are outside this
  change's blast radius; the coordination outlasts the change.
- **Remove the deployment id from the payload.** The id is what the monitors alert on.

## Consequences
- Deployment cadence stays publicly inferable, so a future change that makes cadence
  sensitive reopens this decision rather than inheriting it.
- Adding any non-public field to `/status` is now a decision, not an edit.

## Accepted-risk
THREAT-004 — anonymous enumeration of deployment ids via `/status`.

## Accepted-by
Priya Raman, Head of Platform (2026-09-28)

## Binds
REQ-011; change `theme-persistence`; THREAT-004

## Review
On the next change that adds a field to `/status`.
```

## Checklist

- [ ] Every consequential decision in `design.md` has an `ADR-###` file on disk
- [ ] Every ADR has all seven headings in order
- [ ] `Status` is one of the four permitted values
- [ ] At least one rejected alternative is named, with the reason it lost
- [ ] At least one consequence is a cost, not a benefit
- [ ] `Binds:` names a `REQ-###`, a change, or both
- [ ] Every accepted threat carries `Accepted-risk:` and `Accepted-by:` with a person's name
- [ ] No ADR number is reused; no `design.md` reference points at a missing file
- [ ] `Review:` carries a date or a named trigger
- [ ] Every ADR predates the G3 verdict it is offered as evidence for

## Anti-patterns

**The decision with no rival.** `ADR-004 — Use PostgreSQL. We use PostgreSQL everywhere.`
Nothing was chosen, so nothing can be revisited. Either name what PostgreSQL beat and why
(`DynamoDB: the access pattern is relational and the join would move into the application`),
or drop the ADR and state the constraint in `design.md`.

**Consequences that are all upside.** `Consequences: faster, simpler, more testable.` Every
consequential decision costs something. Write the cost:
`the preference now lives on the critical render path, so the user store's availability is
now the page's availability`.

**Editing an accepted decision.** Rewriting `ADR-007`'s `Decision` when the team changes its
mind. Every handoff, test and incident report that cited ADR-007 now describes something that
was never decided. Write `ADR-014` and set `ADR-007` to `Superseded by ADR-014`.

**Role as acceptor.** `Accepted-by: Security team`. A team cannot be asked what it was
thinking in eighteen months. Name the person and the date:
`Accepted-by: Priya Raman, Head of Platform (2026-09-28)`.

**Reason that describes the winner.** `Rejected: Redis. We chose PostgreSQL because it is
already deployed.` That is the winner's reason wearing the loser's label, and it survives no
challenge. Write the loser's property: `Redis: the preference must outlive an eviction, and
sizing the cache to guarantee that costs more than the row does`.

**ADR written after the gate.** G3 recorded on Monday, `ADR-011` written on Thursday because
a reviewer asked where the decision was. The gate attested to evidence that did not exist.
Re-record G3 as `--fail`, write the ADR, then re-record.

**Numbered by directory position.** Allocating `ADR-###` by counting files, so a deleted ADR
frees its number for reuse. The next reader of an old handoff finds a decision that has
nothing to do with the one it cited. Allocate from the highest number ever used.

**Decision recorded in the handoff only.** An envelope saying
`assumptions: ["chose server-side storage"]` with no ADR. `handoffs.md` is a transfer record,
not a decision log; the next change will not read it. Write the ADR and cite it.

## Validation

```bash
# Every ADR referenced by the active change's design resolves to a file
for id in $(grep -o 'ADR-[0-9]\{3,\}' delivery/changes/<name>/design.md | sort -u); do
  test -f "delivery/decisions/$id.md" || echo "MISSING: $id"
done

# Every ADR carries the seven required headings
for f in delivery/decisions/ADR-*.md; do
  for h in Status Context Decision "Alternatives rejected" Consequences Binds Review; do
    grep -q "^## $h$" "$f" || echo "$f: missing '## $h'"
  done
done

# No duplicate numbers, and no status outside the permitted four. Rule 1 mandates one file
# per id at ADR-###.md, so a directory listing can never repeat a number and `ls | uniq -d`
# is vacuous. Read the number each file declares instead: a heading that disagrees with its
# own filename, or two files claiming one number, is the collision that actually happens.
for f in delivery/decisions/ADR-*.md; do
  n=$(basename "$f" .md)
  h=$(grep -m1 -o '^# ADR-[0-9]\{3,\}' "$f" | grep -o 'ADR-[0-9]\{3,\}')
  [ -n "$h" ] || { echo "$f: no '# ADR-### — …' heading"; continue; }
  [ "$n" = "$h" ] || echo "$f: the filename says $n and the heading says $h"
done
grep -ho '^# ADR-[0-9]\{3,\}' delivery/decisions/ADR-*.md | grep -o 'ADR-[0-9]\{3,\}' \
  | sort | uniq -d | sed 's/^/two files claim the same number: /'
grep -A1 '^## Status$' delivery/decisions/ADR-*.md \
  | grep -vE '(Status|^--|Proposed|Accepted|Rejected|Superseded by ADR-[0-9]{3,})'

# Every accepted risk names a person
grep -l '^## Accepted-risk$' delivery/decisions/ADR-*.md \
  | xargs -r grep -L '^## Accepted-by$'
```

Each command prints nothing when the rule holds. The last one lists ADRs that accept a risk
nobody has signed for; every such file blocks G3.
