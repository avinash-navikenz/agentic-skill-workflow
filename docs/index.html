Internal field guide · v0.1.0

An agentic SDLC framework, Plan to Monitor

Agents hold the judgment. Skills hold the rules.

The framework ships 11 persona agents carrying each discipline's judgment, and 50 skills across 13 disciplines carrying each discipline's rules. A nine-verb CLI scaffolds the lifecycle into your repo and records what actually happened at each of nine gates — so a phase that emitted no telemetry did not happen, and a gate whose verdict was never recorded was never passed.

This page is generated from the repository. Every agent, skill, phase, gate, lane, traceability link and validator finding is extracted from the source files by scripts/build_catalogue.py, which also writes the README beside each SKILL.md and each *.agent.md. Add a skill or an agent and re-run it — the catalogue, the counts, the filters and the cross-links all follow; nothing on this page is typed by hand. Every command in the worked demo was run against the committed tree and its output copied verbatim, and what v1 does not do is under Limits.

How the framework works

Four ideas carry the whole design

The falsifiable test. Delete every agent and the skills still fully specify how work is done; delete every skill and the agents still specify what, why and when.

Enforced by scripts/lint_separation.py: SEP1 a numbered procedure inside an .agent.md · SEP2 a ## Template or ## Checklist inside an .agent.md · SEP3 persona voice inside a SKILL.md · SEP4 first person inside a SKILL.md. The build fails on any of them.

The corollary is the part that bites: an agent may not produce a lifecycle artifact from memory. It loads the governing skill, follows it, and records which skills it used in the handoff envelope. An agent that writes a spec from what it remembers about specs has made the skill library decorative.

2 · Nine phases, nine gates, and a loop that closes

Phases are not a waterfall. Phase 6's owner is consulted at phase 2 — testability of an acceptance criterion is cheapest to fix while the criterion is still being written — and the Architect reviews phase 5 output against the design phase 3 settled. Consultation is recorded as a handoff with kind: review, not as a phase transition.

Each gate's exit criteria and the evidence it accepts, straight from ADLC.md §2:

A verdict is one of exactly three values: pass, fail, waived. There is no conditional pass and no pass with follow-ups. --pass and --fail both require --evidence <path>.

3 · Four lanes, as gate subsets

Proportionality is what keeps the framework in daily use. Nine gates on a flag flip is not rigour; it is a guarantee that the next flag flip goes around the framework. The lane is declared at propose time, written into state.lane, and fixed for the life of the change.

Choosing a lane

  • By the highest-severity characteristic present, never the average. One regulated field in an otherwise trivial change makes the whole change full.
  • Anything touching a dataset, schema, feature store or model takes full — see the G4 gap in Limits.
  • hotfix means production is degraded right now. A bug found before release is standard.
  • Where two lanes both fit, take the wider one. An unnecessary gate costs hours; a missing gate costs an incident.

Skipped is not waived

A gate outside the lane's set is skipped: recorded nowhere, and navi-delivery gate refuses it outright with <G#> is not in lane '<lane>'.

A gate inside the set that cannot be met is waived, with a reason and a calendar expiry strictly in the future, appended to .adlc/waivers.md and to the event log. Only one of the two is a decision somebody made.

Lanes are never widened in place. A change that outgrows its lane is closed out — waiving each unsettled gate with a reason naming the abandonment — and re-proposed. There is no abandon verb.

4 · The traceability chain

The spec is the source of truth; code is its consequence. Every artifact after the first declares the upstream ID it descends from, and the chain runs one way only — an insight can propose a new requirement, but by becoming a candidate REQ-### in a new change, never by editing backwards into a closed one.

What the validator actually sees

scripts/validate_traceability.py is deliberately literal. It recognises a requirement only as REQ-### on a line starting with #; a task only as **TASK-###** in bold; and an Implements: REQ-### line only within three lines of its task marker. Three digits minimum — it does not see REQ-4 at all.

This is the single most common way a spec passes validation while meaning nothing.

The findings

Rework: a failed gate does not simply block

validate fails while any stale entry remains, so rework cannot be silently skipped past. Each stale gate is cleared by re-recording that gate individually as pass or waived — a passing G6 does not vouch for G7. Re-recording is a supported path: the event log appends a new record carrying previous, and history is never overwritten.

Two ways in

One item, or the framework

Every item under Agents and Skills carries both of these, written for that item. They are not equivalent, and the difference is the thing worth understanding before you pick one.

One agent, with the skills it holds

$ git clone https://github.com/avinash-navikenz/agentic-skill-workflow.git $ cd agentic-skill-workflow $ ./install.sh --agent navi-agent-<name>

The installer reads the skill list out of the agent’s own file and installs those and nothing else — the Architect brings 16 of the 50, not all of them. The two travel together because an agent loads its skills rather than working from memory. What this leaves out is the lifecycle CLI: no navi-delivery command, so no gates and no delivery record.

One skill on its own is ./install.sh --skill navi-skill-<name>. Nothing in the lifecycle will invoke it — no phase loads it and no gate depends on it, because it is an agent that decides when a skill applies — but you can name it directly in a session. Both flags repeat and combine, and --uninstall takes the same selection: it keeps any skill another installed agent still holds.

The whole framework

/plugin marketplace add avinash-navikenz/agentic-skill-workflow /plugin install navi-delivery@navi-delivery # 50 skills + 11 agents

This is the supported path, and the preferred one: every agent, every skill it holds, and the cross-references between them, with no clone to install. The repository publishes itself as a Claude Code marketplace carrying one plugin, sourced from adapters/claude-code/. install.sh does the same job from a clone and is the right choice when you are editing the framework rather than using it.

install.sh was verified into a scratch directory with CLAUDE_SKILLS_DIR / CLAUDE_AGENTS_DIR pointed at it — 50 skill directories and 11 agent files land, each skill directory carrying both SKILL.md and README.md, and --uninstall removes exactly what it created.

How to get it

Install the adapter, not the repo root

adapters/claude-code/ is the installable artefact. It is generated output with the flat layout the convention uses — skills/<name>/SKILL.md and agents/<name>.md, discipline folded away — plus its own .claude-plugin/plugin.json, so the directory is a complete plugin on its own.

The repository root carries two manifests. .claude-plugin/marketplace.json is the marketplace, and its single plugin entry sources ./adapters/claude-code — so installing through /plugin install never installs the root.

.claude-plugin/plugin.json describes the root itself as a plugin, but the root's skills are nested one level deeper (skills/<discipline>/<name>/SKILL.md). That nesting is how the source is organised so a reader can find things. Whether a harness loads a nested layout correctly is unverified. Do not install the repo root and assume it works.

1 · Install the agents and skills

This repository is a Claude Code plugin marketplace publishing one plugin. Adding it and installing from it is the preferred route — nothing to clone, and /plugin update navi-delivery refreshes it later. Both commands are typed inside Claude Code, not in a shell.

/plugin marketplace add avinash-navikenz/agentic-skill-workflow /plugin install navi-delivery@navi-delivery

Verified against a local checkout rather than the GitHub path: claude plugin validate . passes, the marketplace registers as navi-delivery, and claude plugin install navi-delivery@navi-delivery lands 50 skills and 11 agents. The avinash-navikenz/agentic-skill-workflow form above resolves once that repository is published.

Or from a clone, with install.sh

install.sh installs the same adapters/claude-code/ tree into your Claude directory — symlinks by default, so edits to the repo take effect live. That is what you want when you are changing the framework rather than using it, and it is the form CI runs. It needs a checkout, as does the single-item copy above: both run scripts and copy files out of the repository. The marketplace route above needs none, which is most of why it is the preferred one.

Outside the repository

Connect & observe

Three things that reach past the repository: the MCP connection files two skills use instead of a token in the shell, telemetry that exports the gate ledger to AgentObs, Opik or LangSmith, and an optional cron runner that turns tracker items into proposed branches. All three are off until you configure them, and none is required to use the framework.

MCP

Connection files, with no credential in any of them

navi-skill-work-item-sync reads and writes work items and navi-skill-knowledge-publishing publishes pages. Both prefer an MCP server when the session has one connected, because the server holds the credential — no token reaches the shell, the transcript, or a file in the repository.

$ cp config/mcp/github.mcp.json .mcp.json $ claude mcp add --transport http atlassian https://mcp.atlassian.com/v2/mcp
FileRouteAuthenticates with
atlassian-cloud.mcp.jsonAtlassian's hosted serverOAuth in the browser, as you
atlassian-cloud-token.mcp.jsonmcp-atlassian under uvxan Atlassian Cloud API token
azure-devops.mcp.json@azure-devops/mcp under npxyour az login session
github.mcp.jsonGitHub's hosted serverOAuth in the browser, as you

Every secret in those files is a ${NAME} the harness expands at launch. scripts/validate_mcp_configs.py runs in CI and fails on a value shaped like a known token anywhere in the document, and on any literal under a credential-shaped key — which is what catches an internal credential matching no public pattern. It also fails on a ${NAME} that .env.example does not document, so the variable list cannot drift away from the files that use it.

Prefer a hosted route: it carries no secret for you to leak and acts as you, so the server can do nothing your own account cannot.

Telemetry

One trace per change, one span per gate

$ navi-delivery telemetry doctor $ navi-delivery telemetry preview --out payload.json # sends nothing $ navi-delivery telemetry export --backend langsmith

What it exports

The ledger: who recorded which gate, when, with what evidence, how long the change waited between decisions, how many times a gate was re-recorded. That is what this framework knows and nothing else does.

A gate decision is an instant, so its span has no duration. The number a delivery dashboard actually wants is on the span as navi.since_previous_ms — recorded as what it is, rather than dressed up as a measured duration.

What it does not

The agents' own model calls — prompts, completions, tokens, cost. The CLI makes none, so it has none to report, and claiming otherwise would be exactly the promise its own skills exist to stop people making.

Instrumenting the agents and the product is a different job, and a different skill: agent observability carries the span register, the derived ids, the capture decision and the dated proof that spans arrived and rendered.

BackendEndpoint variableCredential → header

The one way this can silently do nothing. llm.span.kind is AgentObs's own convention with no OpenTelemetry meaning. AgentObs renders only the kinds it recognises; one it does not know is accepted, stored, and shown on no screen, with no error on either side — a failure that looks exactly like success. Probe with NAVI_OTLP_SPAN_KIND (agent, workflow, chain, task) before trusting a dashboard. Opik and LangSmith ignore the attribute.

Credentials come from the environment only, are never printed — doctor shows header names, not values — and never reach delivery/.adlc/telemetry.json, the local record of what was sent and whether it arrived. A refused export exits non-zero and changes nothing about the delivery record: a gate that was recorded stays recorded whether or not a trace reached a vendor.

Optional

Tracker item to proposed branch, on a schedule

For each tagged work item it has not seen, the runner branches off the base, runs propose, seeds the proposal from the item, commits, pushes and opens a pull request. What it opens is a scaffolded branch, not a proposal — a person still writes the why.

$ node automation/cron/navi-cron.js --config automation/cron/navi-cron.jira.example.json $ ./automation/cron/install-cron.sh --config /abs/path/config.json # prints the line

Three properties, each with a test. It never touches the checkout it runs in — every change happens in a worktree it creates and removes. It does nothing irreversible without --push. And tracker text never reaches a shell as code: anyone can file a ticket, so configured commands take their values from the environment and quote them themselves, which a test proves by filing an item whose title tries to touch a canary file.

Any tracker that can be queried from a shell works: the integration surface is one command printing a JSON array of {id, title, url}. The shipped examples reshape Jira and Azure Boards output into it with jq.

First: one agent doing its job

Before the whole lifecycle, the smaller unit. At Phase 3 the Architect takes a signed-off spec and produces design.md, the ADRs and the handoffs. What makes it an agent rather than a prompt is that it does not write any of those from memory — it loads the governing skill for each, and it knows the four or five situations in which it stops and asks a person.

propose writes design.md with one heading per G3 exit criterion, so a heading left with its placeholder is a criterion nobody answered. The Architect fills each in place:

delivery/changes/add-csv-export/design.md — as scaffolded
# Design — add-csv-export

> G3-DESIGN is read against this file. Every heading below is one of G3's exit criteria, so a
> heading left with its placeholder is a criterion nobody answered.

## Approach
## Alternatives rejected
## Decisions          | ADR | Decision | What it binds |
## Interface contracts
## Quality attributes
## Failure modes      | Failure mode | Behaviour when it occurs | Detected by |
## Threat model
## Risks
## Linked artifacts   | Artifact | Path | Written under |

Two of those sections are where the judgment lives on a change this size. Decisions: ADR-001 records choosing streaming serialisation over building the whole file in memory, and what that binds — a choice with no rival option is not an ADR, and belongs under Approach as a constraint. Threat model: a CSV export of an on-screen report is a reach change even though it adds no data, because it turns "visible to someone at a screen" into "a file that leaves the building". Every threat ends as designed out, mitigated, or accepted by a named person.

    New requirements go in the change's delta spec, not in delivery/specs/. The validator scans both, so a requirement is traceable from the moment it is written, and archive folds the delta into delivery/specs/ at the end.

### REQ-001 — Export a report as CSV
**Priority:** Must

An analyst can download the report currently on screen as a CSV file.

#### AC-001
Given a report with at least one row,
when the analyst opens it,
then a `Download CSV` control is present.

#### AC-002
Given the analyst activates `Download CSV`,
when the file is opened,
then its header row names every visible column, in display order.

#### AC-003
Given a report with zero rows,
when the analyst opens it,
then no `Download CSV` control is present.

    AC-003 is the one that earns its place. G6 requires that negative and empty-state criteria are covered, not only the happy path — and it is the criterion this change is about to fail on.

    delivery/changes/add-csv-export/tasks.md
    # Tasks — add-csv-export

- [ ] **TASK-001** Add the CSV serialiser.
  - Implements: REQ-001
- [ ] **TASK-002** Add the download route and the control, hidden on an empty report.
  - Implements: REQ-001

    Both task ids are bold, and each Implements: line sits directly under its task. Neither is cosmetic: an unbolded task is invisible to the validator, and an Implements: line more than three lines from its marker is prose.

Honesty

What v1 does not do

These are real, recorded, and worth knowing before you meet them. All verified against the committed tree at f8707d3; the ones that are still true are still true, and the reasoning behind every ruling made during the v1 build is in docs/DECISIONS.md.

Only two adapters are built

Claude Code (adapters/claude-code/) is supported and exercised. Generic (adapters/generic/RUNBOOK.md) is the paste-in fallback.

Codex and Cursor have sibling manifests at the repo root (.codex-plugin/, .cursor-plugin/) and doctor detects both harnesses and maps their capabilities — but no adapter tree is built for either in v1, and neither has been loaded in its harness. LangGraph, CrewAI and other SDK harnesses are named in the design and not built. Use the generic RUNBOOK there today.

gate --evidence checks shape, never content

Evidence must be a regular, non-empty file — a directory, a device and a zero-byte file are each refused, and a symlink is judged by what it resolves to. That is the whole of the check. The file is never opened. One character of anything is accepted:

$ printf 'x' > $E/g6.md && navi-delivery gate G6 --pass --evidence $E/g6.md
G6 pass (evidence: …/evidence/g6.md, by: dev@navikenz.com)

The gate records that evidence was named and that something is there to open, not that it says what you claim. A human reviewing the change is what establishes the second. Treat the path as a citation and make it one a reader can follow.

The actor on a gate event is derived, not proven

Every gate event now carries actor and actor_source, so a gate co-owned by two agents — G3 by the Architect and the Security Engineer, G6 by the QA Engineer and the Security Engineer — can show which owner recorded the verdict. But unless --actor or $NAVI_DELIVERY_ACTOR was used, the name is whatever git config user.email or the shell login happened to say. It is a label, not an authentication. actor_source is what lets a reader tell a deliberate name (flag, env) from an inferred one (git, login) — check it before trusting a name.

There is also no second-party approval step: the person who records a waiver is the person accepting the debt, and the Approved by column in waivers.md is that same derived name. The G9 archived event carries no actor at all.

G4 is enforced only on the full lane

The original design described standard as enforcing "G4 only if data or ML is touched". cli/lib/lanes.js implements standard as a fixed set that does not contain G4, and gate refuses anything outside the set. A standard change that turns out to touch data or a model therefore cannot record G4 at all.

Until that is reconciled, navi-skill-lane-selection routes anything touching a dataset, schema, feature or model to full at proposal time. Discovering it mid-change is a re-proposal, not a lane edit.

A waiver attaches to the whole gate

One reason and one expiry cover every criterion the gate checks, so a single unfixable finding waives the gate rather than itself. G8 checks an SLI, a runbook and telemetry confirmed arriving; one waiver silences all three.

A failed gate writes no rework record

ADLC.md §4 says a --fail writes a rework record to changes/<name>/handoffs.md naming the phase to re-enter, the gate, the artifacts implicated and the reason. No CLI command touches handoffs.md after propose scaffolds it — after the G6 failure in the demo, the file still held its empty template.

The stale-marking and the validate block are real and were verified. The rework record is an agent's job, written by hand under navi-skill-handoff-protocol.

validate lints the framework, not only your repo

validate_manifests.py and lint_separation.py always run against the installed framework tree; only the traceability check runs against your delivery/. So validate reports 50 framework files whichever repo you run it in — as it does in the worked demo.

Separately, navi-skill-code-review is not exercised by the validation harness: its substantive checks read a live authenticated pull request, which neither a fixture nor CI can supply. It is declared unharnessable, deliberately and visibly, rather than stubbed.

Maturity. Every agent and skill in the catalogue carries maturity: draft and version: 0.1.0. The version stays put until the framework is stable in real use.
