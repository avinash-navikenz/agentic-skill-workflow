Worked demo

One change, carried end to end

add-csv-export: a feature inside an existing capability, touching no data and no model, so the lane is standard. Every block below was run against the committed tree at f8707d3, in a scratch directory, and its output copied verbatim — including the part where G6 fails and the change goes back for rework, which is the part worth reading twice. The narrative version with the reasoning behind each artefact is docs/WALKTHROUGH.md; this is the same change, condensed to what you type and what comes back.

First: one agent doing its job

Before the whole lifecycle, the smaller unit. At Phase 3 the Architect takes a signed-off spec and produces design.md, the ADRs and the handoffs. What makes it an agent rather than a prompt is that it does not write any of those from memory — it loads the governing skill for each, and it knows the four or five situations in which it stops and asks a person.

propose writes design.md with one heading per G3 exit criterion, so a heading left with its placeholder is a criterion nobody answered. The Architect fills each in place:

delivery/changes/add-csv-export/design.md — as scaffolded
# Design — add-csv-export

> G3-DESIGN is read against this file. Every heading below is one of G3's exit criteria, so a
> heading left with its placeholder is a criterion nobody answered.

## Approach
## Alternatives rejected
## Decisions          | ADR | Decision | What it binds |
## Interface contracts
## Quality attributes
## Failure modes      | Failure mode | Behaviour when it occurs | Detected by |
## Threat model
## Risks
## Linked artifacts   | Artifact | Path | Written under |

Two of those sections are where the judgment lives on a change this size. Decisions: ADR-001 records choosing streaming serialisation over building the whole file in memory, and what that binds — a choice with no rival option is not an ADR, and belongs under Approach as a constraint. Threat model: a CSV export of an on-screen report is a reach change even though it adds no data, because it turns "visible to someone at a screen" into "a file that leaves the building". Every threat ends as designed out, mitigated, or accepted by a named person.

Then: the whole framework carrying that change

  1. Scaffold, and open the change

    init writes delivery/, generates AGENTS.md from the agent and skill tree, and detects the harness. It is idempotent per repo. The lane is chosen now, before any work, and cannot be widened later.

    init · propose · status
    $ navi-delivery init
Initialised delivery/ (harness: claude-code)
Next: navi-delivery propose <name> --lane standard

$ navi-delivery propose add-csv-export --lane standard
Created delivery/changes/add-csv-export (lane: standard; gates: G1 · G2 · G3 · G5 · G6 · G7 · G8)

$ navi-delivery status
change: add-csv-export
lane:   standard
phase:  1

  G1  pending
  G2  pending
  G3  pending
  G5  pending
  G6  pending
  G7  pending
  G8  pending

    Note what propose told you: seven gates, not nine. G4 and G9 are outside this lane's set, and navi-delivery gate G4 will refuse outright rather than record a skip.

  2. Write the spec — a requirement and its acceptance criteria

    New requirements go in the change's delta spec, not in delivery/specs/. The validator scans both, so a requirement is traceable from the moment it is written, and archive folds the delta into delivery/specs/ at the end.

    delivery/changes/add-csv-export/specs/reporting/spec.md
    # Capability — Reporting

### REQ-001 — Export a report as CSV
**Priority:** Must

An analyst can download the report currently on screen as a CSV file.

#### AC-001
Given a report with at least one row,
when the analyst opens it,
then a `Download CSV` control is present.

#### AC-002
Given the analyst activates `Download CSV`,
when the file is opened,
then its header row names every visible column, in display order.

#### AC-003
Given a report with zero rows,
when the analyst opens it,
then no `Download CSV` control is present.

    AC-003 is the one that earns its place. G6 requires that negative and empty-state criteria are covered, not only the happy path — and it is the criterion this change is about to fail on.

    delivery/changes/add-csv-export/tasks.md
    # Tasks — add-csv-export

- [ ] **TASK-001** Add the CSV serialiser.
  - Implements: REQ-001
- [ ] **TASK-002** Add the download route and the control, hidden on an empty report.
  - Implements: REQ-001

    Both task ids are bold, and each Implements: line sits directly under its task. Neither is cosmetic: an unbolded task is invisible to the validator, and an Implements: line more than three lines from its marker is prose.

  3. Validate

    validate --strict
    $ navi-delivery validate --strict

0 finding(s) across 50 file(s)

0 separation finding(s)

0 traceability finding(s)
validate: OK

    Three checks ran. The first two lint the framework's own agents and skills, not your repo — they report 50 files whichever repo you run them in. Only the third, traceability, is about your change. --strict adds T4: is any task actually building this requirement? Run it before G5; a requirement with no task is scope that was specified and then quietly dropped.

    Delete the three AC- blocks from that spec and the third check is the one that speaks up — a requirement nothing can test:

    a T2 finding
    $ navi-delivery validate --strict

0 finding(s) across 50 file(s)

0 separation finding(s)
T2 …/delivery/changes/add-csv-export/specs/reporting/spec.md: REQ-001 has no acceptance criteria

1 traceability finding(s)
validate: FAILED
exit 1

  4. Record gates — evidence first, verdict second

    gate G1 · G2 · G3 · G5
    E=delivery/changes/add-csv-export/evidence
$ navi-delivery gate G1 --pass --evidence $E/g1-intent.md
G1 pass (evidence: delivery/changes/add-csv-export/evidence/g1-intent.md, by: dev@navikenz.com)
$ navi-delivery gate G2 --pass --evidence $E/g2-spec.md
G2 pass (evidence: delivery/changes/add-csv-export/evidence/g2-spec.md, by: dev@navikenz.com)
$ navi-delivery gate G3 --pass --evidence $E/g3-design.md --actor priya@navikenz.com
G3 pass (evidence: delivery/changes/add-csv-export/evidence/g3-design.md, by: priya@navikenz.com)
$ navi-delivery gate G5 --pass --evidence $E/g5-build.md
G5 pass (evidence: delivery/changes/add-csv-export/evidence/g5-build.md, by: dev@navikenz.com)

    Every verdict is attributed. The name is derived — --actor first, then $NAVI_DELIVERY_ACTOR, then git config user.email, then the OS login — and the event records which of those answered, in actor_source. G3 above was recorded deliberately by a named person (flag); the rest fell through to the git identity (git). That distinction is the point: a name typed on purpose is stronger evidence than one inferred from whichever shell happened to be open.

    Phase 4 is skipped, not waived, and nothing is recorded. Three shapes of bad evidence are each refused with their own message, and nothing is written:

  5. G6 fails, and the rework propagates

    The suite runs and AC-003 fails: the Download CSV control still renders on an empty report. The happy path works; the empty state does not.

    gate G6 --fail

    G7 and G8 went stale because a release decision made on top of a failed verification is a decision about a different change. G1–G5 did not: those were decided on evidence that is still good. Rework cannot be walked past. That is the entire mechanism.

  6. Fix it, re-record, and waive what cannot be met

    re-record · release · waive
    $ navi-delivery gate G6 --pass --evidence $E/g6-tests.md
G6 re-recorded: fail -> pass (evidence: delivery/changes/add-csv-export/evidence/g6-tests.md, by: dev@navikenz.com)

$ navi-delivery gate G7 --pass --evidence $E/g7-release.md
G7 pass (evidence: delivery/changes/add-csv-export/evidence/g7-release.md, by: dev@navikenz.com)

$ navi-delivery gate G8 --waive "Export volume SLI lands with the reporting \
    dashboard in the next platform release" --expires 2026-12-31
G8 waived until 2026-12-31 (approved by: dev@navikenz.com)

    re-recorded: fail -> pass. The event log appends a new record carrying previous: "fail"; it does not overwrite the old one. And re-recording G6 cleared gate:G6 and nothing else — G7 and G8 were each recorded on their own.

    The expiry is the entire control on a waiver, so the CLI checks it properly. Each of these is refused, and nothing is written:

    four refused waivers
    $ navi-delivery gate G8 --waive "x" --expires 2020-01-01
--expires '2020-01-01' must be strictly in the future
$ navi-delivery gate G8 --waive "x" --expires 2026-02-30
--expires '2026-02-30' is not a real calendar date
$ navi-delivery gate G8 --waive "x" --expires soon
--expires must be a calendar date in YYYY-MM-DD form, got 'soon'
$ navi-delivery gate G8 --waive "x"
a waiver requires --expires <YYYY-MM-DD>

    A row lands in delivery/.adlc/waivers.md:

    delivery/.adlc/waivers.md
    | Date | Change | Gate | Reason | Expires | Approved by |
|------|--------|------|--------|---------|-------------|
| 2026-09-30 | add-csv-export | G8 | Export volume SLI lands with the reporting dashboard in the next platform release | 2026-12-31 | dev@navikenz.com |

    The Approved by cell carries the resolved actor: this CLI has no second-party approval step, so the person who records a waiver is the person accepting the debt.

    A waiver covers the whole gate. G8 checks several things — an SLI, a runbook, telemetry confirmed arriving — and this one reason waives all of them. Write the reason so the next reader can tell which criterion was actually in question.

  7. Archive, and close the loop

    status · archive
    $ navi-delivery status
  G1  pass
  G2  pass
  G3  pass
  G5  pass
  G6  pass
  G7  pass
  G8  waived

$ navi-delivery archive add-csv-export
Archived to delivery/changes/archive/2026-09-30-add-csv-export
Insights: delivery/ops/postmortems/add-csv-export.md — route each to the backlog or a skill amendment

    Every gate in the lane is settled, nothing is stale, and the delivery tree traces, so archive proceeds. It refuses on any of the three, naming what is outstanding and changing nothing — the traceability check matters most here, because archive is the moment the claim becomes permanent:

    archive refusing a change that does not trace
    $ navi-delivery archive x
cannot archive 'x': traceability findings are outstanding. Nothing was changed.
T3 …/delivery/changes/x/tasks.md: TASK-001 implements unknown REQ-999

1 traceability finding(s)
  resolve by binding each task to a requirement that exists, and giving every requirement acceptance criteria
  re-check with: navi-delivery validate
exit 1

    On the clean change, three things happened: the delta spec was folded into delivery/specs/reporting/spec.md, which is now the current truth about what the system does; the change moved to changes/archive/2026-09-30-add-csv-export/ intact; and an insight stub was written.

    delivery/ops/postmortems/add-csv-export.md — the stub, then filled
    # Postmortem — add-csv-export

## What we learned

- **INSIGHT-001** <what changed in our understanding>
  - Destination: product backlog | skill amendment
  - Target: <REQ candidate, or the navi-skill-* to amend>

## KPI vs actual
<what we predicted, what happened>
    the loop closing
    - **INSIGHT-001** The empty-state criterion was written but not built, and only the
  test caught it. Every criterion that describes an absence is at risk of this.
  - Destination: skill amendment
  - Target: navi-skill-test-design — require an explicit check that negative and
    empty-state criteria have a test before G5 is recorded, not at G6.

    Every INSIGHT-### names exactly one destination: the product backlog, as a candidate REQ-### for a future change, or a skill amendment — a pull request against a navi-skill-* file. The second path is the whole point. This change failed G6 on an empty-state criterion; the insight routes to the skill that governs test design, so the next team loads a standard that already knows about it. An insight with no destination closes no loop and is not an insight.

  8. The event log is the record

    Everything above is in delivery/.adlc/events.jsonl, append-only. status, validate and archive read only this and state.json — a verdict asserted in prose and never recorded does not exist.

    delivery/.adlc/events.jsonl
    {"ts":"…","gate":"G1","verdict":"pass","evidence":"…/g1-intent.md","actor":"dev@navikenz.com","actor_source":"git"}
{"ts":"…","gate":"G2","verdict":"pass","evidence":"…/g2-spec.md","actor":"dev@navikenz.com","actor_source":"git"}
{"ts":"…","gate":"G3","verdict":"pass","evidence":"…/g3-design.md","actor":"priya@navikenz.com","actor_source":"flag"}
{"ts":"…","gate":"G5","verdict":"pass","evidence":"…/g5-build.md","actor":"dev@navikenz.com","actor_source":"git"}
{"ts":"…","gate":"G6","verdict":"fail","evidence":"…/g6-failures.md","actor":"dev@navikenz.com","actor_source":"git"}
{"ts":"…","gate":"G6","verdict":"pass","evidence":"…/g6-tests.md","actor":"dev@navikenz.com","actor_source":"git","previous":"fail"}
{"ts":"…","gate":"G7","verdict":"pass","evidence":"…/g7-release.md","actor":"dev@navikenz.com","actor_source":"git"}

    The G6 failure is still there, with its evidence path and the name of who recorded it, next to the pass that carries previous: "fail". Six months on, that pair is the answer to "why does the export hide itself on an empty report". archive writes a final G9 archived event even on standard, where G9 is not in the enforced set — it marks the close-out, not a gate verdict, and it is the one event in the file that carries no actor.

    Timestamps elided as … for width; the real file carries a full ISO-8601 instant and the full evidence path on every line.

Never run a navi-delivery command with the framework repo as its working directory. init and propose write a delivery/ tree wherever they are run. Use the repo you actually work in, or a scratch directory.
