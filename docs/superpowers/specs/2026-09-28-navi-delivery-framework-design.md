## 1. Intent

Teams doing day-to-day project work should be able to drop one framework into any repo and
get a complete, governed lifecycle from **Plan through Monitor** — driven by AI agents that
hold the *judgment* of each engineering persona, backed by skills that hold the *rules and
best practices* of each discipline.

`navi-delivery` is that framework. It is modelled on two existing things:

- **OpenSpec** — for the artifact model: a directory scaffolded into the consuming repo,
  specs as source of truth, changes as proposals, a validated lifecycle, tool-agnostic entry
  via a generated `AGENTS.md`.
- **Superpowers** — for the distribution model: a zero-dependency plugin carrying a skills
  library, loaded across many harnesses from one tree via sibling manifests.

The new contribution is the layer neither has: **persona agents over best-practice skills**,
covering the full lifecycle rather than the coding slice of it.

### Success criteria
1. A team runs `navi-delivery init` in an existing repo and ships a real change through the
   framework the same day, without reading more than the README.
2. The same agents and skills run unchanged in Claude Code, Codex, Cursor, and a bare chat
   loop with no plugin support.
3. A change of any size — a config flag or a regulated ML capability — has a proportionate
   path through the framework, so nobody routes around it.
4. Every shipped change is traceable from requirement to running telemetry.

### Non-goals (v1)
- Not a project-management tool. No ticket sync, no sprint mechanics, no estimation engine.
- Not a code generator. It governs how code is specified, reviewed, tested and operated.
- Not a package manager. Persona packs are folders, not independently versioned artifacts.
- No web UI, no server, no external service dependency.

**Corrected against what shipped.** Three entries in the original tree were never built and
have been removed: `.agents/plugins/` (the cross-runtime alias — nothing needed it once
`adapters/generic/RUNBOOK.md` existed), `schemas/` (JSON Schema per artifact type — the
validators check structure directly against the Markdown, so a schema layer would have been
a second, unenforced description of the same rules), and `templates/adlc/`, which shipped as
`templates/change/` and `templates/delivery/` because the two payloads have different
lifetimes: one is copied per change, the other once per repo.

**`npx navi-delivery <cmd>` does not work.** The package is `private: true` and unpublished,
so there is no registry entry for `npx` to fetch. The CLI is reached by `npm install
--global .`, which installs the `navi-delivery` bin, or by `node cli/index.js` on a path.
Four validators shipped where the design named three; `adapters/`, `registry/`, `tests/` and
`docs/` were present in the build and absent from the design's tree.

├── changes/archive/YYYY-MM-DD-<name>/
├── decisions/ADR-###.md
├── ops/
│   ├── slo.md                  # SLI-### definitions
│   ├── runbooks/
│   └── postmortems/            # → INSIGHT-###

`ops/` is the deliberate extension beyond OpenSpec, which ends at archive. Phases 8–9 need a
home in the repo or the loop cannot close.

### 3.3 Conventions

Skills are `navi-skill-<descriptive-name>` inside a discipline folder. Agents are
`navi-agent-<persona>` as `*.agent.md`. Frontmatter follows the house shape but drops
`pillar`/`group` in favour of self-describing fields:

```yaml
---
name: navi-skill-acceptance-criteria
description: >
  Use when writing or reviewing acceptance criteria for a requirement. Defines the
  Given/When/Then form, objective-testability rules, and AC-### numbering.
  Trigger phrases include: acceptance criteria, AC, given when then, testable requirement,
  definition of done for a requirement.
allowed-tools: Read Write Edit Grep
metadata:
  version: "0.1.0"
  maturity: draft
  kind: skill
  discipline: spec-driven-development
  lifecycle_phases: [2, 6]
  used_by_agents: [navi-agent-business-analyst, navi-agent-qa-engineer]
  owner: avinash.negi@navikenz.com
  tags: "sdd, requirements, quality"
  model: sonnet
---
```

Agents use the same block with `kind: agent`, plus `owns_gates`, `skills`, `capabilities`,
`consumes`, `produces`, `handoff_to`, `escalate_to_human_when`.

## 4. The agent/skill contract

### 4.1 The separation law

- **Agents hold judgment** — mission, mental model, decision heuristics, trade-off framing,
  escalation triggers, definition of good, and a skill-invocation plan.
- **Skills hold rules** — standards, decision tables, templates, checklists, anti-patterns,
  and a mechanical validation step.

**Falsifiable test:** delete every agent and the skills still fully specify *how* work is
done; delete every skill and the agents still specify *what, why and when*.

**Operational test for a rule in disguise.** A sentence in an agent is misplaced when **both**
hold: (a) it tells the reader what to do, or what an artifact must contain, **and** (b) it adds
no reason the governing skill does not already carry. A sentence that names a boundary the
persona will not cross, or that gives a *reason* for choosing between permitted options, is
judgment — **even when a skill covers the same mechanics**. An agent may restate a constraint
when it says *why* that constraint binds it.

*This replaces an earlier formulation, "a sentence present in both belongs in the skill", which
was unsatisfiable: every escalation condition an agent states also lives in a skill, so the rule
forbade agents from stating their own boundaries while this same section requires exactly that.
Five review passes produced a rising count (2, then 9, then 14, then 15) — the signature of an
unsatisfiable definition rather than a defective codebase. A companion test, "could a reader
comply with this mechanically", was also withdrawn: a good reason is compliable, which is what
makes it useful, so that test deleted judgment along with rules.*

**Enforcement:** `lint_separation.py` fails the build on a numbered procedure or a template
inside an `.agent.md`, and on second-person persona voice ("as the Architect, weigh…")
inside a `SKILL.md`. Without a mechanical check the two halves merge within months.

**Corollary:** an agent may not produce a lifecycle artifact from memory. It loads the
governing skill and follows it, then records which skills it used in the handoff envelope.

#### Reconciliation of §4.3 against what shipped

**`security/` was missing from the catalogue entirely.** The design placed every
security concern inside other disciplines — `threat-modelling` under `architecture/`,
`secure-coding` under `software-development/` — because §10 open question 3 had not yet
answered whether a Security Engineer existed. Once it did (see §10), a discipline folder
followed: an agent's discipline is a real field in its frontmatter, and a Security Engineer
whose discipline named somebody else's folder would have been the first lie in the
manifest. `security/navi-skill-dependency-vulnerabilities` is what shipped there in v1.
`threat-modelling` stayed under `architecture/` on purpose — it is exercised at G3 beside
the design decisions it constrains, and moving it would have split the G3 evidence across
two disciplines for no gain. `secure-coding` stayed under `software-development/` for the
same reason: it governs code review and the handling of untrusted input, which is where a
developer looks for it.

**`secure-coding` shipped as [v1] without carrying the marker here.** It is in the
Security Engineer's and the Full Stack Developer's skill lists and is exercised by the
Validation harness. The marker was simply never added when the scope grew; corrected above.

**The counts moved for two reasons, not one.** 37 → 39 is the two security-adjacent skills
the eleventh agent needed: `dependency-vulnerabilities` as a genuinely new skill, and
`secure-coding` pulled forward out of the tail. 11 → 12 disciplines is the `security/`
folder. The full catalogue therefore moves 56 → 57: one skill was added to the total, and
one moved from the tail into v1, leaving 18 scoped-but-unbuilt skills rather than 19. No
further `security/` skills are scoped; if a `secrets-management` or similar is wanted, it is
new scope and should arrive as an `INSIGHT-###` routed to a skill amendment, not as a
catalogue entry written here in advance.

**Per-discipline v1 counts as shipped**, which is what `validate_manifests.py` sees:
`lifecycle-method` 6 · `software-development` 5 · `spec-driven-development` 4 ·
`architecture` 4 · `platform-devops` 4 · `data-engineering` 3 · `machine-learning` 3 ·
`quality-engineering` 3 · `business-analysis` 2 · `product-management` 2 · `mlops` 2 ·

### 4.4 Capability portability

Agents declare neutral capabilities. Every capability has a mandatory fallback — that
requirement is what makes "runs in any harness" true rather than aspirational.

| Capability | Claude Code | Codex / Cursor | Bare chat loop fallback |
|---|---|---|---|
| `read_file` | Read | file read | ask the human to paste |
| `write_file` | Write | file write | emit in a fenced block |
| `run_command` | Bash | shell | ask the human to run and paste output |
| `search` | Grep/Glob | search | ask for the relevant paths |
| `ask_human` | AskUserQuestion | prompt | plain question, then wait |
| `spawn_subagent` | Agent | — | adopt the persona sequentially in one session |

A persona is a **subagent** where subagents exist and a **role the model steps into** where
they do not — same agent file, same skills, degraded isolation only.

`build_adapters.py` projects the agent and skill tree into each harness manifest. Adapters
are generated, never hand-edited; `navi-delivery doctor` detects the harness and reports which
capabilities are native versus falling back.

### 4.5 Handoff envelope

Each phase transition appends a block to `changes/<name>/handoffs.md`:

```yaml
- from: navi-agent-business-analyst
  to: navi-agent-architect
  phase: 2 → 3
  artifacts: [REQ-001..REQ-014, AC-001..AC-031]
  skills_used: [navi-skill-spec-authoring, navi-skill-acceptance-criteria]
  assumptions: ["Peak load assumed 500 rps — unconfirmed"]
  open_questions: [Q-003]
  confidence: medium
```

Handoffs are not purely linear: QA is consulted at phase 2 for testability, the Architect
reviews phase 5 output. Consultation is recorded as a handoff with `kind: review`.

## 5. Lifecycle model

### 5.1 Phases and gates

| # | Phase | Gate | Owner |
|---|---|---|---|
| 1 | Plan | G1-INTENT | Product Owner |
| 2 | Specify | G2-SPEC | Business Analyst |
| 3 | Architect | G3-DESIGN | Architect |
| 4 | Data & Model | G4-DATA-MODEL | Data + ML Engineer |
| 5 | Build | G5-BUILD | Developer / Data / ML |
| 6 | Verify | G6-QUALITY | QA Engineer |
| 7 | Release | G7-RELEASE | DevOps + MLOps |
| 8 | Operate & Monitor | G8-OPERATE | MLOps + DevOps |
| 9 | Learn & Evolve | G9-FEEDBACK | Product Owner + Architect |

Mapped onto the change lifecycle: `explore → propose → design → apply → verify → release →
operate → archive`.

**Gate identifiers: `G1` through `G9`.** The suffixed forms above — `G2-SPEC`,
`G3-DESIGN` and the rest — appear throughout this document, in agent descriptions and in
`navi-skill-phase-gate-protocol/references/gates.md`, while `owns_gates` frontmatter,
`cli/lib/lanes.js`, `state.json`, `events.jsonl` and the `navi-delivery gate` argument all
use the bare form. That is not a drift to be fixed in one direction: **`G1`–`G9` are the
identifiers, and the suffix is descriptive only** — a mnemonic for a human reader, never a
string a tool matches. `G2` and `G2-SPEC` name the same gate; only `G2` is ever typed. This
is now stated in `ADLC.md` §1 so a reader meets it before meeting both spellings.

**Owners, as shipped.** G3 is co-owned by the Architect and the Security Engineer; G6 by the
QA Engineer and the Security Engineer. The G4, G5, G7, G8 and G9 rows already named two or
more owners. Gate events record no actor, so a co-owned gate's event cannot show which owner
recorded it — see §8.

### 5.2 Lanes

Proportionality is what keeps the framework in daily use. The lane is declared in
`proposal.md`; the orchestrator enforces the matching gate set.

| Lane | Trigger | Gates enforced |
|---|---|---|
| `express` | copy, config, flag flip | G2, G6, G7 |
| `standard` | most features and bugs | G1, G2, G3, G5, G6, G7, G8 (G4 only if data/ML touched; G9 batched) |
| `full` | new capability, regulated, or any ML | all nine |
| `hotfix` | production incident | G6, G7 immediately; G2 retroactive within 48h; G9 postmortem mandatory |

A skipped gate is always **recorded** in `events.jsonl`, never silent. Waivers require a
reason and an expiry in `.adlc/waivers.md` — enforced by `navi-skill-waivers-and-deferrals`.

#### Diverged in v1: `standard` does not enforce G4 conditionally

The table above describes `standard` as enforcing "G4 only if data/ML touched".
`cli/lib/lanes.js` implements `standard` as a **fixed** set — `G1, G2, G3, G5, G6, G7, G8` —
and `navi-delivery gate` refuses any gate outside the active lane's set outright. A
`standard` change that turns out to touch data or a model therefore **cannot record G4 at
all**.

The divergence was deliberate. A lane whose gate set depends on a property the CLI cannot
observe would have to either ask a human at every `gate` call or infer "touches data" from
the diff, and both make the lane's meaning unpredictable at proposal time — which is the one
moment the lane exists to settle. A fixed set per lane is checkable, testable in the golden
path, and readable from one file.

The cost is that lane selection now carries the condition instead:
`navi-skill-lane-selection` rule 4 routes **anything** touching a dataset, schema, feature
store or model to `full`, and discovering it mid-change is a re-proposal rather than a lane
edit. That is a worse experience for a small data change than the design intended, and it is
the honest trade. If it proves too coarse in use, the fix is a conditional gate set with an
explicit `--touches-data` flag on `propose`, recorded in `state.json` at proposal time — not
an inference at `gate` time.

#### Diverged in v1: a waiver's scope is the whole gate

`gate --waive` attaches one reason and one expiry to a gate. A gate such as G6 checks many
criteria, so a single unfixable finding waives every criterion the gate covers rather than
waiving itself. The design did not specify a finer granularity and the implementation did not
invent one; per-criterion waivers would need criteria to be addressable IDs, which they are
not today. Recorded here so it is a known limit rather than a surprise; `README.md` and
`ADLC.md` both state it to the user.

#### Also true of `gate --evidence`

The evidence check is existence, not content: any path that resolves is accepted, **including
an empty directory**. The gate records that evidence was named. This is not a divergence —
the design never claimed content inspection — but it is the most commonly misread part of the
gate contract, so it is stated here as well as in `ADLC.md` §2.

### 5.3 Rework

A failed gate does not simply block. The orchestrator writes a rework record naming the
phase to re-enter and marks every downstream artifact `stale`. `navi-delivery validate` fails
while stale artifacts exist, so rework cannot be silently skipped. Specs change first, code
second — a code change that outruns its spec is a defect, not a shortcut.

### 5.4 Traceability

`REQ → AC → ADR → TASK → TEST → SLI → INSIGHT`. Each artifact declares upstream IDs.
`navi-delivery validate --strict` fails on orphans: code with no TASK, TASK with no REQ, REQ
with no AC, shipped capability with no SLI.

### 5.5 State and resumability

`.adlc/state.json` holds the current change, lane, phase, gate verdicts, and stale set. A
fresh session in any harness reads it and resumes mid-flight rather than re-deriving. Long
deliveries exceed any context window; without this the framework fails on its second day.

### 5.6 Loop closure

Archiving emits `INSIGHT-###` records. Each targets one of two destinations:

1. **Product backlog** — a candidate REQ for a future change.
2. **Skill amendment** — a PR against a `navi-skill-*` file.

The second path is how the framework improves from use instead of ossifying. A postmortem
that reveals a wrong standard should change the standard.

## 7. Quality strategy

The framework's content *is* the product, so it is tested like product:

- **`evals/evals.json` per skill**, in the existing house format — so `/skill-creator`,
  `/eai-eng-skills-evaluator` and `skill-batch-creator` all work on this repo unchanged, and
  the long tail beyond v1 can be bulk-generated.
- **`lint_separation.py`** — the separation law, mechanically.
- **`validate_manifests.py`** — frontmatter, naming, and referential integrity. **Rules M1
  through M7**, not M1–M6 as the implementation plan named them: `M1` frontmatter parses ·
  `M2` required keys present for the kind · `M3` `name` matches its directory and its
  kind's prefix · `M4` every name in an agent's `skills:` resolves to a real skill ·
  `M5` every skill is named by at least one agent · `M6` a skill's `description` contains
  `Trigger phrases include:` · **`M7` a skill's `metadata.used_by_agents` equals exactly the
  set of agents that list it.** M7 was added during implementation and is reported in two
  directions, because the fix differs: one direction means the skill's claim is stale, the
  other means an agent acquired the skill without being recorded. Without it the two sides of
  that invariant could drift while M4 and M5 both stayed clean.
- **`validate_traceability.py`** — rules T0–T4, the ID chain of §5.4. Not named in the
  original quality strategy; §5.4 described the check without naming the script.
- **`validate_skill_checks.py`** — runs each skill's own `## Validation` block against its
  own `## Template`, then against a mutation that violates a rule the block claims to check.
  A check that stays silent on the violation fails. A skill absent from
  `scripts/skill_harness.yaml` fails too, so a new skill cannot arrive with unexercised
  checks. Shipped state: **38 harnessed · 1 declared-unharnessable · 0 failing.** The
  exception is `navi-skill-code-review`, whose substantive checks read a live authenticated
  pull request through `gh api graphql`; neither a fixture nor CI can supply one, and
  stubbing `gh` would leave the harness asserting the stub. It is declared unharnessable
  visibly rather than quietly skipped.
- **`lint_separation.py`** rules are `SEP1`–`SEP4`: a numbered procedure in an agent, a
  Template or Checklist section in an agent, persona voice in a skill, first person in a
  skill.
- **`golden_path.py`** — a toy project carried through all four lanes in CI, asserting
  artifacts exist, gates recorded, zero orphans. The regression test for the whole system.
- **Harness matrix** — `doctor` detects the harness and reports native versus fallback
  capabilities. **Diverged in v1:** CI does not run `doctor` per adapter. Only the
  `claude-code` and `generic` adapter trees are built, and `doctor`'s detection is driven by
  environment variables rather than by the adapter directory, so a per-adapter matrix would
  have asserted the environment CI happens to run in rather than the adapter. The capability
  table is instead generated into every adapter from one source, `registry/capabilities.json`,
  and CI fails if the generated adapters differ from a fresh build.

## 8. Failure modes and handling

| Failure | Handling |
|---|---|
| Agent cannot complete a phase | Escalate per `escalate_to_human_when`; record blocked state; never fabricate an artifact |
| Gate fails | Rework record; downstream marked stale; validate blocks |
| Human checkpoint unavailable | Block. Never self-approve a human decision |
| Harness lacks a capability | Fall back per §4.4; `doctor` reports degradation |
| Context exhausted mid-change | Resume from `state.json` |
| Skill and agent conflict | Skill wins on *how*; agent wins on *whether* |
| Two agents disagree | Orchestrator arbitrates; unresolved → human checkpoint |

#### Known limitation: gate events record no actor

An `events.jsonl` record carries `change`, `gate`, `verdict`, `evidence` (or `reason` and
`expires`), and `previous` where the gate is being re-recorded. It does **not** carry who
recorded it. For a gate owned by one agent that is recoverable from the roster; for G3 and
G6, each co-owned by two agents, it is not — the log cannot show whether the Architect or the
Security Engineer recorded G3.

This was not a decision so much as an omission that only became visible once the eleventh
agent made two gates genuinely co-owned. It is not fixed in v1 because adding an actor field
raises a question the CLI cannot answer on its own — an agent is not an authenticated
identity, so a self-declared actor is an assertion, not a fact. The route worth taking is to
require the actor on the command line and treat it as a claim recorded alongside the
evidence, the way the release approval already names its approving human.

## 10. Open questions — answered

Each question is kept with its original framing; the answer is recorded beneath it.

1. **`owner` email** to stamp in agent and skill metadata.
   **Answered: `avinash.negi@navikenz.com`.** Stamped into all 11 agent files and all 39
   `SKILL.md` files, replacing the `OWNER_TBD` placeholder, and carried into the generated
   adapters. The literal survives only in `tests/lint` fixture data, where it is test input
   rather than metadata, and in this design's implementation plan and task briefs, which are
   historical records.

2. **Orchestrator** — distinct agent, or collapsed into the CLI?
   **Answered: kept as a distinct agent**, as the design proposed. Lane selection and rework
   arbitration are judgment. The CLI enforces the mechanical half — it refuses a gate outside
   the lane, refuses a waiver without a real future expiry, and refuses to archive while
   anything is unsettled — and the orchestrator holds the half that requires a reason.
   `navi-agent-orchestrator` ships with `owns_gates: []`, which is the visible statement of
   the split: it routes and arbitrates, and owns no gate of its own.

3. **Additional personas.** Security Engineer and UX/Product Designer.
   **Answered: Security Engineer yes, UX/Product Designer no.**
   `navi-agent-security-engineer` shipped, owning phases 3 and 6, co-owning G3 with the
   Architect and G6 with the QA Engineer, and bringing a `security/` discipline with it. The
   reason is the one the question itself identified: for regulated work, a threat model that
   nobody owns is a document rather than a decision, and both G3 and G6 had exit criteria
   that presumed an owner who did not exist.
   The UX/Product Designer gap is **open and deliberate**. `frontend-standards` remains
   unbuilt in the tail, and no v1 change in the golden path exercises a design decision. An
   agent with one unbuilt skill would have been a roster entry rather than a persona.

4. **`prompts/agentic-sdlc-system.prompt.md`** — absorb into `ADLC.md`, or keep standalone?
   **Answered: kept standalone, and not absorbed.** They are different artifacts for
   different readers. `ADLC.md` documents the lifecycle *of this framework as built*, for
   someone using it. The prompt is a generator: a self-contained instruction for building a
   framework of this kind from nothing, in any harness, with placeholders to fill. Folding
   it into `ADLC.md` would have produced a document that was half reference and half
   instruction and correct as neither, and deleting it would have discarded the only record
   of how the framework's own shape was derived. It is listed in §3.1 under `prompts/`.
   The overlap is real and is accepted: the prompt's phase table and this document's §5.1
   describe the same nine phases, so a change to the lifecycle has to be made in both.

5. **Stack opinionation.**
   **Answered: stack-neutral rules with a `project.md` override**, as the design's own
   leaning had it. `templates/delivery/project.md` is the human-authored place a team names
   its stack and conventions, and the `software-development` skills are written to be read
   against it. The alternative — house defaults — would have made the framework undroppable
   into any repo whose stack disagreed, which contradicts §1's first success criterion.
